        Alodokter, 2019–2024

        Production scale and reliability

        I joined the e-pharmacy in its early stage and stayed as it grew to 700+ orders a day. The 90% drop in failed orders didn't come from one optimization: it came from fixing three separate failure modes. From 2022 I led the team of 5 that ran it.

        • 3
          separate failure modes behind the 90% drop
        • < 30 min
          medication delivery through partner integrations
        • 60+
          production releases covered by my documentation
        Read the full case studyHide the full case study

        Every order coordinated external systems: pharmacy partners for stock and fulfilment, courier partners for delivery. As volume grew, each weak point between them turned into failed orders: before this work, failed orders were an almost daily issue, mostly checkout timeouts and partner out-of-stock rejections.

        1. Stock that wasn't really there

          ProblemAn item showed as available, then the pharmacy partner rejected the order as out of stock. Stock synchronization also caused resource spikes.

          What changedStock synchronization moved into a separate stock engine on its own VM. It processed partner stock and updated the availability the shop reads, so a sync spike no longer competed with checkout for CPU and memory.

          In an integration-heavy system, your own database is not the only source of truth.

          Looking backThe engine still wrote straight into the shop's database. That was the pragmatic step at the time; today I would keep the isolation and pass stock updates through an internal API or events.

        2. A checkout doing too much

          ProblemEvery order triggered a recalculation of stock across every warehouse and partner pharmacy, inside the synchronous checkout request. A pattern inherited from earlier code, and slow requests ended as timeouts.

          What changedI took the full recalculation out of checkout, so the request only does what has to happen before the customer gets a response, and added eager loading and indexes to the queries that remained.

          Keep the critical transaction path as small as possible.

        3. Orders created twice

          ProblemRepeated or concurrent requests could create duplicate orders.

          What changedOrder creation was protected against repeated and concurrent requests.

          A retry must never become a second transaction.

          How I build it todayAn idempotency key per checkout attempt, stored with the order it created, backed by a database unique constraint. Redis locking only if a real cross-server race calls for it.

            Vessels, crew, fishing gear and trip manifests all follow the same lifecycle. Each gets its own policy and service pair instead of one shared class full of conditionals, so a new record type is added without touching the ones that already work.

            Authorization in three independent checks

            1. Right applicationDepartment officers and fishing companies use separate surfaces; the route rejects the wrong one
            2. Exactly one capabilityEach policy owns one permission resource, and a role either has that action or doesn't
            3. Only your rowsEach fishing company sees only its own data, and a per-record ownership check is the last line of defense

            Rules enforced by tooling, not memory

            • A custom RBAC linter and policy contract tests fail the build if a policy shares a permission, falls back to another resource, or checks permissions outside the base policy.
            • Architecture rules live in the repository for human contributors and AI coding agents alike, with one definition of done: RBAC lint, RuboCop, tests and Brakeman all pass.
            • Records freeze the reference data they depend on at filing time, with a full audit trail, so later edits to master data never rewrite history.
            • Staging deploys on every push; production deploys need a human reviewer's approval.

            Engineering workflow

            Engineering should be a system, not a collection of heroes.

            Every step protects a different part of delivery. Choose a step to see what happens there.

              Part of this comes from Michael Gerber's The E-Myth: consistent quality comes from systems people can follow, not from exceptional individuals. The same is true of engineering teams.

              Leadership: capacity planning

              A new task should change the plan, not silently increase someone's workload.

              Every request is logged, estimated and planned, so the cost of new scope is visible before anyone commits to it.

              In practice: the work nobody planned for

              Not every request arrives as a ticket. A client asks for an architecture diagram for a proposal, a UI mockup, a quick issue check, or an analysis of whether something can be built at all. That work is real, but it rarely makes it into a plan, so it quietly lands on whoever is available.

              What typically arrives unplanned

              • Architecture diagrams for client proposals, usually mine
              • UI/UX designs in Figma
              • Issue investigations
              • Feasibility analysis of client requests
              1. Log it the moment it arrivesAs an additional task in the development plan, whoever picks it up, including me.
              2. Estimate it, or record what it really tookIf the effort is clear, it gets a man-day estimate before work starts. Exploratory work like a feasibility check or an investigation is logged as it happens and gets its actual effort recorded when done, instead of a guess.
              3. RebalanceThe next planning pass evens out the load across developers, so nobody carries work the plan can't see.

                How I learned to lead

                When the team was two developers, I could hold every decision myself. As it grew across three countries, that habit became the bottleneck: I had been treating "doing as much as possible myself" as responsibility. John C. Maxwell's books changed that view, from personal execution to multiplying people. Now I hand work over once someone can do it about 70% as well as I would, and invest in the context, standards and review that close the rest of the gap.

                What changed

                • A junior developer who started without version control was running a production platform on his own, including releases and incident response, within about three months.
                • Developers I mentored progressed from needing guidance to independently owning projects and DevOps responsibilities.
                • An apprentice with no framework or version-control experience was contributing production work within his first two months.

                I used to think responsibility meant doing as much as possible myself. Leadership turned out to mean building people who can take responsibility without depending on me.
